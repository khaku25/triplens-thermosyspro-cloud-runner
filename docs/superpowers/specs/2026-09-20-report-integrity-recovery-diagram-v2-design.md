# TripLens 보고서 무결성·복구 워크플로·로직 도면 V2 설계

**작성일:** 2026-09-20  
**기준 브랜치:** `origin/main` (`858f2d4`)  
**배포 원칙:** GitHub 검증 완료 전 Vercel 배포 금지

## 1. 목적

현재 TripLens 화면과 고장보고서 초안은 원인 후보와 근거를 연결하지만 다음 문제가 있다.

1. 업로드 원본 EVENT가 서버에서 보강한 EVENT보다 우선되어 보고서의 `관련 태그`에 실제 Source 태그 대신 `TRIP_LATCH`, `FLOW_LOW` 같은 이벤트 분류가 기록될 수 있다.
2. 실제 조회 Evidence Catalog가 일부 EVENT만 포함할 때 전체 SOE가 참조하는 근거 중 일부가 `증거자료` 섹션에서 누락된다.
3. 자동 발생 EVENT가 `시간대별 조치사항`으로 표시되어 운전원 조치와 혼동된다.
4. 복구 화면은 `UNKNOWN` 고정 문구만 보여 실제 조치·복구·승인 정보를 입력할 수 없다.
5. 원인 분석 화면은 상세 정보가 기본 노출되고 기술 식별자가 반복되어 핵심 판단과 미완료 항목이 잘 보이지 않는다.
6. draw.io 도면은 입·출력은 구분하지만 조건, 동작, 지연, 복귀/히스테리시스가 중앙 블록에 섞여 있다.

이 변경은 보고서의 참조 무결성을 보장하고, 사고 사건과 사람의 조치를 분리하며, 복구 상태를 명시적으로 입력·보존하고, 로직 도면을 `입력 → 조건 → 동작 → 출력` 구조로 읽을 수 있게 한다.

## 2. 범위

### 포함

- 전체 EVENT와 실제 조회 RAW Evidence의 손실 없는 병합
- 보강 EVENT 우선 병합 및 정확한 Source 태그 사용
- 보고서 내부 Evidence ID 참조 무결성 검사
- SOE와 운전원·정비 조치의 분리
- 복구 상태·시각·수행자·조치·재기동 조건·근거·승인자 입력과 브라우저 보존
- 입력 검증, 원인 검증, 복구 상태, 문서 상태의 독립 표시
- 원인·사건 상세의 점진적 공개와 모바일 보고서 카드 배치
- 근거 상세의 도면 버튼 명칭 명확화
- draw.io schema 2와 입력/조건/동작/출력/추가정보 배치
- 회귀 테스트 및 GitHub CI 검증

### 제외

- `/testbench` 화면, `IntegrationTestbench.js`, 단위기기 fixture와 그 판정 로직
- Gemini 프롬프트와 원인판정 알고리즘 변경
- EVENT/RAW 원본 파일 변경
- ThermoSysPro 물리모델 변경
- Vercel 배포

정적 단위기기 테스트는 현재 동작과 문구를 그대로 유지한다. 생성된 draw.io 자산의 새 schema를 읽는 것은 허용하지만 테스트벤치 자체 코드는 수정하지 않는다.

## 3. 데이터 병합 규칙

### 3.1 EVENT 병합

EVENT identity는 `evidence_id || event_id`이다.

1. 업로드 EVENT를 먼저 Map에 넣는다.
2. `/bootstrap` 및 `/analyze`가 돌려준 보강 EVENT를 같은 ID에 덮어쓴다.
3. 같은 필드가 양쪽에 있으면 서버 보강값이 우선한다.
4. `source_node`, `canonical_tag`, `logic_ids`, `mapping_status`는 보강값을 보존한다.
5. 결과는 `model_time_s` 오름차순, 동일 시각은 원래 EVENT 순서로 유지한다.

### 3.2 보고서 Evidence Catalog

보고서용 Catalog는 다음 합집합이다.

```text
전체 병합 EVENT + 실제 조회되어 제공된 RAW/EVENT evidence_catalog
```

- 모든 EVENT는 `source_kind: EVENT`로 보고서 증거자료에 포함한다.
- 조회 Catalog에 같은 EVENT ID가 있으면 더 상세한 조회 Catalog 값이 우선한다.
- RAW는 실제 조회된 표본만 포함한다. 원본 RAW 전체를 AI가 읽었다고 표시하지 않는다.
- 보고서에서 참조하는 비어 있지 않은 모든 Evidence ID는 증거자료에 존재해야 한다.
- 참조가 끊기면 내보내기 전에 명시적인 무결성 오류를 표시하며 정상 상태처럼 내보내지 않는다.

### 3.3 태그와 이벤트 유형

- `관련 태그`: `source_node || canonical_tag || tag`
- `이벤트 유형`: `event_class || tag`
- `비고`: 이벤트 원천/유형을 표시

`TRIP_LATCH`, `BREAKER_OPEN`, `FLOW_LOW` 같은 분류값을 Source 태그 대신 사용하지 않는다.

## 4. 보고서 구조

보고서 V2의 사람용 섹션은 다음 10개로 정리한다.

1. 개요
2. 사고 발생 전 운전 현황
3. 장애 현상
4. 시간대별 사건·자동동작(SOE)
5. 발생 원인
6. 운전원·정비 조치사항
7. 조치 결과 및 복구 판정
8. 추정 원인 및 미확인 사항
9. 재발방지 대책 — 검토 권고사항
10. 증거자료

SOE에는 EVENT 기반 트립, 차단기 동작, 경보를 넣는다. 운전원·정비 조치에는 사람이 입력한 실제 확인·조작·정비 내용만 넣는다. 조치가 없으면 `추가 확인 필요`와 `UNKNOWN`을 유지한다.

CSV는 기존 8개 열을 유지한다.

```text
구분, 항목, 내용, 상태, 근거 ID, 관련 태그, 기록 시각, 비고
```

값·단위·상태·매핑 상세는 증거 ID를 통해 앱 상세 및 PINPOINT.csv에서 확인한다. 사람용 CSV를 유일한 기계 감사자료로 표현하지 않는다.

## 5. 복구 상태 모델

복구 입력은 별도 상태 객체로 유지한다.

```text
status: UNKNOWN | PARTIAL | RECOVERED | NOT_RECOVERED
recovered_at: string
operator: string
actions: string
restart_conditions: string
evidence_ids: string
approver: string
```

### 상태 규칙

- 기본값은 `UNKNOWN`이다.
- `RECOVERED` 또는 `PARTIAL`인데 조치 내용·수행자·복구시각 중 하나라도 비어 있으면 `복구 입력 미완료`로 표시한다.
- 승인자가 비어 있으면 문서는 계속 `초안`이다.
- 원인 Verification Gate와 복구 승인은 서로 독립이다.
- `Evidence Policy PASS`는 입력 근거 준비 통과일 뿐 원인 확정이나 복구 승인을 뜻하지 않는다.

복구 객체는 브라우저 세션에 함께 저장한다. 파일을 교체하거나 입력·분석을 지우면 기본값으로 초기화한다.

내보내기 시 복구 객체가 다음 보고서 행의 권위 있는 원천이다.

- `운전원·정비 조치사항 > 실제 수행 조치`
- `조치 결과 및 복구 판정 > 복구 상태`
- `조치 결과 및 복구 판정 > 재기동 조건`
- `조치 결과 및 복구 판정 > 담당자·승인자`

## 6. 화면 정보 구조

### 6.1 공통 진행 상태

분석 결과가 존재하면 상단에 네 상태를 함께 표시한다.

- 입력 근거: PASS/HOLD
- 원인 검증: PASS/HOLD
- 복구 판단: UNKNOWN/PARTIAL/RECOVERED/NOT_RECOVERED
- 문서: 초안/승인대기

각 상태는 범위를 한글로 설명하고 서로 대신하지 않는다.

### 6.2 입력 영역

- 분석 전에는 파일 카드와 처리 흐름을 기본 노출한다.
- 분석 후에는 파일명과 상태만 간결히 보이고 Run ID, digest, Logic version, Prompt version은 `감사·버전 정보` 접힘 영역에 넣는다.

### 6.3 사고 진행 과정

- Critical Events는 기본 노출한다.
- 전체 EVENT 표는 `전체 SOE 보기` 접힘 영역에 둔다.

### 6.4 원인 분석

- Primary Cause와 Direct Trigger는 기본 노출한다.
- Propagation, Causal Chain, 반대 근거, Tool trace는 각각 접힘 영역에 둔다.
- 긴 Evidence ID와 태그는 줄바꿈한다.

### 6.5 보고서 편집

- 데스크톱에서는 8열 표를 유지한다.
- 좁은 화면에서는 각 행을 필드 라벨이 있는 카드로 표시하여 페이지 가로 스크롤을 만들지 않는다.
- 참조 무결성 오류가 있으면 누락 ID 목록을 표시한다.

## 7. 근거 상세과 버튼 명칭

분석 화면의 근거 상세에서 다음 명칭을 사용한다.

- `태그 기준 도면 · {tag}`
- `운전조건·룰 기준 도면 · {rule}`

태그 기준 도면은 선택 태그가 사용·생성되는 관계를 보여주고, 운전조건·룰 기준 도면은 하나의 등록 룰의 입력·조건·동작·출력을 보여준다. `/testbench`의 기존 버튼 문구는 이번 변경에서 수정하지 않는다.

## 8. draw.io schema 2

생성 루트는 `triplens_schema="2"`를 사용한다.

각 룰은 왼쪽에서 오른쪽으로 다음 네 열을 갖는다.

1. `INPUT / 입력`
2. `CONDITION / 조건`
3. `OPERATION / 동작`
4. `OUTPUT / 출력`

`ADDITIONAL INFO / 추가정보` 상자는 동작 블록 아래 또는 우측 하단에 작게 배치하며 다음 값을 표시한다.

- 동작 지연
- 복귀/히스테리시스
- 원장 검증 상태
- 출력 분류

입·출력 박스에는 태그 ID, 설명, 단위를 정렬해 표시한다. 조건 박스에는 조건식만, 동작 박스에는 Rule ID·로직명·로직 유형만 표시한다. 추가정보는 신호선에 연결하지 않는다.

연결선은 다음 구조만 갖는다.

```text
입력 → 조건 → 동작 → 출력
```

schema 1의 `logic:{rule}` 위치를 새 동작 블록에 무리하게 재사용하지 않는다. schema 2용 안정 ID를 사용해 최초 생성 시 새 열 배치를 적용한다. 태그와 룰의 의미 ID, 해시 검증, draw.io 저장 기능은 유지한다.

## 9. 오류 처리

- 끊어진 보고서 Evidence ID가 있으면 UI에 누락 목록을 표시한다.
- CSV/PDF/PINPOINT 내보내기 버튼은 무결성 오류 상태에서 비활성화한다.
- 복구 미입력은 오류가 아니라 `초안/승인대기` 상태로 처리한다.
- Logic 자산 해시 또는 schema가 일치하지 않으면 기존처럼 fail-closed 한다.
- 원본 EVENT/RAW는 어떤 편집에서도 변경하지 않는다.

## 10. 테스트 기준

### 보고서 무결성

- 21개 EVENT와 14개 조회 Evidence를 입력해도 증거자료에는 21개 EVENT가 모두 존재한다.
- SOE 15~21을 포함해 모든 참조 ID가 증거자료에서 해소된다.
- 업로드 원본의 `TRIP_LATCH`보다 보강 EVENT의 `vppGTTripLatch`가 관련 태그로 선택된다.
- SOE는 `시간대별 사건·자동동작(SOE)`에, 사람 조치는 별도 섹션에 배치된다.

### 복구

- 기본 UNKNOWN과 필수 입력 누락을 구분한다.
- 복구 입력이 보고서 행, PDF, CSV에 동일하게 반영된다.
- 세션 저장/복원과 파일 교체 초기화를 검증한다.

### 화면

- 상태 네 종류가 동시에 구분되어 보인다.
- 모바일에서 페이지 전체 가로 오버플로가 없다.
- 상세 영역은 접힘/펼침 가능하고 핵심 원인은 기본 노출된다.

### draw.io

- schema 2가 생성된다.
- 각 룰에 조건·동작·추가정보 블록이 하나씩 존재한다.
- 입력→조건→동작→출력 edge가 유효하다.
- 히스테리시스는 동작 본문이 아니라 추가정보에 존재한다.
- 생성 XML, 색인, viewer 자산 해시가 일치한다.

### 회귀

- 기존 백엔드 근거·인용·시간구간 테스트를 모두 통과한다.
- 정적 단위기기 테스트 소스와 fixture는 변경하지 않는다.
- Next.js production build를 통과한다.

## 11. 완료 조건

- 실제 업로드 CSV와 같은 비대칭 Catalog 조건에서 끊어진 Evidence가 0개다.
- 사람용 보고서에서 자동 SOE와 사람의 조치가 구분된다.
- 복구 입력을 작성하고 세션 복원 후에도 유지할 수 있다.
- 원인·복구·문서 상태를 한 화면에서 오해 없이 구분할 수 있다.
- draw.io 모든 룰 페이지가 schema 2 형식으로 재생성된다.
- 단위기기 테스트 코드는 변경되지 않는다.
- GitHub CI 성공 전에는 Vercel을 갱신하지 않는다.
